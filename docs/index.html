Correct: Does PEP 484 require Python to enforce type hints at runtime?

No. PEP 484 explicitly states that Python will remain a dynamically typed language, and the authors have no desire to ever make type hints mandatory, even by convention. 04 / Tool-using agent

Every action leaves a trace.

  • Does PEP 484 require Python to enforce type hints at runtime?

    No. PEP 484 (and the related PEP 3107/typing proposal) specifies type hints only for static type checkers and other third-party tools; they are passive annotations that do not trigger any runtime type checking. As stated in the evidence, "no type checking happens at runtime" under this model—type hints are meant to be analyzed by separate off-line static type checkers, not enforced by the Python interpreter itself.

    answered · 2 steps ↗
  • Why does PEP 526 favor annotation syntax over type comments for parsing?

    Because type comments aren't actually part of the language syntax, any tool that wants to parse them must implement a custom parser rather than being able to rely on the standard `ast` module. Annotation syntax, by contrast, is a core part of the grammar, so it's parsed natively by `ast` and can even be introspected at runtime via `__annotations__`.

    answered · 2 steps ↗
  • Which PEP defines the field-annotation syntax used by data classes, and what limitation does it identify for type comments on uninitialized variables?

    PEP 526 defines the variable/field annotation syntax (e.g., `name: type` or `name: type = value`) used by data classes. It identifies that one limitation of the older type-comment approach (used before PEP 526) is that "there's no way to annotate the type of an undefined variable; one needs to initialize it to None (e.g. a = None # type: int)." PEP 526's new syntax fixes this by allowing a variable to be annotated without an initial value, e.g. `captain: str # Note: no initial value!`.
